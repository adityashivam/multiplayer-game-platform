# Ludo Table implementation plan

> **For agentic workers:** Implement independent rules/server, 3D rendering, and client/HUD tasks against the contracts below, then integrate and review. Preserve all completed voice changes.

**Goal:** Ship a colorful two-player online Ludo game with expressive 3D dice/piece animation and the existing platform voice controls.

**Architecture:** Ludo owns pure board rules, a server-authoritative discrete action protocol and Three.js rendering. The existing platform owns rooms, countdowns, snapshots, voice, input widgets, landscape/fullscreen presentation and dialogs. Event-driven board play uses authoritative revision recovery rather than a movement predictor.

**Tech stack:** Existing JavaScript ES modules, Three.js, React platform, Socket.IO and Node tests. No dependencies, hosting changes, commits or publishing.

## Product and visual direction

- The user selected two humans for quick room starts. Red and yellow play opposite sides of a full four-color board; rules can accept up to four configured human seats later. No bots or fake players are advertised.
- A premium, bright tabletop: ivory raised track tiles, coral/emerald/gold/blue lacquered homes and rounded glossy pawns on a deep navy beveled board. Soft lighting and shadows, restrained highlights and readable active-turn cues.
- The board is the dominant workspace. A compact game-owned side panel shows players, current turn, die value, roll action, four selectable pieces and concise rules. Keep the platform toolbar/voice above the game without inventing another microphone UI.
- Dice tumble and bounce to the server result; legal pieces pulse subtly; pieces hop cell by cell with landing, capture-return and home celebrations. Respect reduced motion, never alter logical coordinates for visual effects and never animate snapshots as new actions.
- Click/tap a legal pawn, or use arrows to select and A/Space/Enter to roll/confirm; number keys select a legal piece. A configurable platform touch Confirm button uses the same action. Input is blocked by platform modals and while the game is awaiting an authoritative action.

## Rules variant

Four pieces per player; a six releases a piece onto its colored start. Clockwise travel has 51 outer positions (progress0..50), five home-lane positions51..55 and exact finish56. Eight marked safe cells permit shared occupancy without capture. Outside safe cells, two same-color pieces form an opponent blockade; opponents may not cross or land on it. Own non-safe stacks are limited to two pieces. A normal landing captures a single opponent and returns it to its yard. Six, capture and finishing a piece earn another roll; three consecutive sixes forfeit the turn. First player with all four pieces home wins. Roll and piece choice each have a30-second decision clock; timeout passes the turn. These choices are the implemented variant, not a claim that all regional Ludo rules are identical.

## Shared contracts

`public/games/ludo/shared/config.js` owns identifiers, board geometry, palette and timing. Pure `rules.js` exports:

- `createLudoRound({playerIds=LUDO_PLAYER_IDS,roundId=1}={})`.
- `getLudoTokenCell(color,progress,tokenIndex)` returning `{column,row}`.
- `getLegalLudoTokenIndices(state,playerId,diceValue=state.diceValue)`.
- `applyLudoRoll(state,playerId,diceValue,nowMs)` and `applyLudoMove(state,playerId,tokenIndex,nowMs)` mutate only legal actions and return boolean acceptance.
- `advanceLudoRound(state,nowMs)` performs bounded phase/deadline transitions.

Snapshot fields: `roundId,revision,playerIds,players,started,startAt,gameOver,winner,currentPlayerId,phase,diceValue,rollSerial,consecutiveSixes,phaseEndsAtMs,turnEndsAtMs,lastMessage,lastAction`. Players contain `id,color,tokens:[progress,progress,progress,progress],connected,finished,captures,seriesWins`. The pure rules retain `legalTokenIndices`; the wire omits this variable-length array and the browser derives it from authoritative board/die state using the same rules. Server-only ownership tokens never enter snapshots.

Phases are `roll|rolling|choose|moving|pass|finished`. Last action always has `{id,kind,playerId,tokenIndex,from,to,diceValue,startedAtMs,durationMs,capturedPlayerId,capturedTokenIndex}`; kind is `none|roll|move|pass|capture|finish`. An action identity is `(roundId,lastAction.id)`. Snapshots are complete bounded state; no action-history queue is needed for recovery.

Inputs are `{type:'roll',roundId,revision}` or `{type:'move',roundId,revision,tokenIndex}`. The server obtains dice through `crypto.randomInt(1,7)`, never a client value; injected dice functions are allowed for tests. Current player, phase, revision, round, connection and legal move are checked before randomness/mutation. Duplicate, stale, out-of-turn and forged commands are ignored. Room pauses invalidate pending actions and preserve board/turn deadlines until resumed through the shared countdown. Rematches preserve seats, series results and voice while resetting the board with a new roundId.

Renderer: `createLudoRenderer({canvas,onPiecePick,onDicePick})` returns `resize(width,height,reservedRightPx=0)`, `render({snapshot,playerId,selectedTokenIndex,nowMs,serverNowMs,reducedMotion,pendingRoll})`, `setQuality(profile)`, `resetPresentation()`, `dispose()`. Picking callbacks receive `(playerId,tokenIndex)` and no arguments for die. All resources/listeners belong to this renderer. It fits the supplied host and does not request fullscreen/orientation. Use action identities and bounded/monotonic animation progress; initial hydration and stale actions snap to authoritative positions. Reset the presentation baseline only upon the first accepted post-join snapshot, allowing a recreated room to restart action IDs without remounting the canvas or accepting stale packets during an existing session.

Client main composes the platform `getGameSocket`/`createGameRoomConnection`, renderer, HUD, game controls, performance settings and results/rematch bridge. Metadata uses `/games/ludo`, `/ludo`, module canvas runtime `/games/ludo/dist/main.js`,10Hz snapshots, null movement input protocol/template, and room seats p1/p2. Shared voice attaches automatically to the existing room connection.

## Tasks

1. Rules/server: pure rules plus rule tests; Ludo registration/server state, revision validation, crypto dice, deadline/pause/rematch behavior and regression tests.
2. Renderer: procedural board/pawns/die, efficient render-cadence animation, picking, quality/resizing/disposal and focused pure animation tests if useful.
3. Client/HUD: room/snapshot recovery, controls, game-owned responsive HUD, results/rematch integration and client event behavior tests.
4. Root integration: catalog/cover/build registration, developer instructions and real browser testing with two clients, high-latency/stalled delivery, reconnect/rematch and actual platform voice.

## Review focus

- Dice pip orientation must match every reported result1..6 after tumbling.
- No illegal capture on safe cells; blockades, exact home entry and third-six forfeits are tested.
- Stale/duplicate clicks, wrong players, malformed inputs and pre-pause packets cannot consume randomness or change the board.
- Renderer never replays an old action on10Hz snapshots, reconnect or rematch, and stacked pieces remain distinct.
- Touch/keyboard/picking work within the host; platform dialogs and voice keep focus and never remount the board.

### Implementation verification

- `npm test`: 901 passing tests, including rule playthroughs with two, three and four configured seats, closed command validation, fixed packed snapshots, pause/rejoin/rematch recovery and animation identities.
- `npm run build`: all game bundles and the React platform build successfully without new dependencies.
- Two-client Chrome scenarios passed without added latency and at 150, 300 and 500 ms simulated RTT with 35 ms jitter and periodic 200 ms ordered stalls. Scenarios cover illegal/duplicate commands, releases, blockades, shared safe tiles, captures, exact finishing, rematches, seat recovery, room recreation and stable canvas identity. Final normal/500 ms runs also verify retained die results across repeated unrolled turn timeouts.
- `VOICE_TEST_GAMES=ludo npm run test:voice:browser`: native Opus audio, microphone/listen-only controls, browser processing preferences, live gameplay, mobile layout and leave cleanup passed using synthetic audio.
- `PLATFORM_PRESENTATION_GAMES=ludo npm run test:presentation:browser`: native fullscreen, denied-fullscreen fallback, library restoration and the default 40% opacity touch control passed.
- Desktop, landscape touch and catalog artwork screenshots inspected. Independent review fixes cover recreated-room animation baselines, retained die faces and non-announced timer refreshes. A scoped monotonic clock mock also removes a pre-existing timing-dependent Sky Dash snapshot-test failure; its production behavior is unchanged.

These are local correctness checks, not a capacity benchmark or a guarantee of real-device rendering speed, real microphone noise removal, global latency or TURN connectivity. Deployment and a two-device network call remain separate checks.
